# Crab Office Implementation Plan

## 1. Цель проекта

Собрать монорепозиторий платформы, в которой пользователь задает запрос на создание офиса, Python-сервис генерирует состав и поведение ИИ-агентов, Java-бэкенд сохраняет состояние и транслирует события, а Next.js-фронтенд визуализирует офис в пиксель-арт стиле в реальном времени.

## 2. Целевой результат MVP

К концу MVP система должна уметь:

- принять запрос пользователя из UI;
- создать комнату с набором агентов через Python AI-service;
- сохранить комнату и агентов в PostgreSQL через Java backend;
- отрисовать офис на фронтенде;
- передавать в UI события статусов агентов через WebSocket;
- использовать Redis для межсервисного Pub/Sub;
- запускаться локально через `docker-compose.yml` для инфраструктуры и отдельные dev-команды для сервисов.

## 3. Архитектурная схема

### Основной поток

1. Пользователь вводит запрос на [frontend-nextjs](frontend-nextjs).
2. Frontend вызывает Java API: `POST /api/rooms`.
3. Java backend отправляет запрос в Python AI-service.
4. Python AI-service обращается к OpenRouter и возвращает JSON с комнатой и агентами.
5. Java backend сохраняет сущности `Room` и `Agent` в PostgreSQL.
6. Java backend публикует событие создания комнаты в WebSocket-канал.
7. Frontend строит офис и отображает агентов.
8. При изменении состояния агента Python публикует событие, Java принимает его и ретранслирует в frontend.

### Зоны ответственности

- `ai-service-python/`: генерация состава офиса, логика агентов, интеграция с OpenRouter.
- `backend-java/`: orchestration, REST API, WebSocket, PostgreSQL, Redis, история.
- `frontend-nextjs/`: UI, анимации, визуализация комнаты, получение realtime-событий.
- `docker-compose.yml`: PostgreSQL и Redis для локальной разработки.

## 4. Фазы реализации

## Phase 0. Базовая подготовка репозитория

Цель: подготовить каркас монорепозитория и базовые документы.

Задачи:

- создать корневой `docker-compose.yml`;
- добавить `.env.example` для Python и Java сервисов;
- определить единые имена портов и переменных окружения;
- описать команды запуска в README;
- зафиксировать JSON-контракт между Python и Java.

Результат:

- понятная структура проекта;
- единый локальный способ запуска инфраструктуры;
- прозрачные контракты между сервисами.

## Phase 1. Инфраструктура и контракты

Цель: поднять инфраструктуру и согласовать API до начала активной разработки.

Задачи:

- настроить `docker-compose.yml` с сервисами `postgres` и `redis`;
- определить базовые порты:
  - frontend: `3000`
  - backend: `8080`
  - ai-service: `8000`
  - postgres: `5432`
  - redis: `6379`
- спроектировать payload для создания комнаты;
- спроектировать payload событий агентов;
- договориться о каналах WebSocket/STOMP.

Предлагаемые контракты:

`POST /api/rooms` в Java:

```json
{
  "prompt": "Построй уютный офис для команды разработки",
  "preset": "cozy"
}
```

Ответ Python на генерацию комнаты:

```json
{
  "roomName": "Cozy Dev Office",
  "theme": "cozy",
  "layout": {
    "width": 12,
    "height": 8,
    "backgroundPreset": "cozy"
  },
  "agents": [
    {
      "externalId": "agent-architect-1",
      "name": "Crab Architect",
      "role": "architect",
      "position": { "x": 2, "y": 3 },
      "state": "idle"
    }
  ]
}
```

Событие агента для Redis и WebSocket:

```json
{
  "roomId": 1,
  "agentExternalId": "agent-architect-1",
  "eventType": "AGENT_MOVED",
  "state": "walking",
  "position": { "x": 4, "y": 3 },
  "message": "Agent moved to design desk",
  "timestamp": "2026-04-12T10:00:00Z"
}
```

Результат:

- инфраструктура запускается;
- контракты согласованы до реализации сервисов.

## Phase 2. AI-service на FastAPI

Цель: реализовать минимальный рабочий Python-сервис.

Файлы и задачи:

- `main.py`
  - поднять FastAPI;
  - реализовать health-check;
  - добавить endpoint генерации комнаты;
  - добавить endpoint приема/эмуляции событий агентов.
- `architect.py`
  - инкапсулировать запрос к OpenRouter;
  - валидировать и нормализовать JSON ответа;
  - предусмотреть fallback-мок при недоступности модели.
- `agent_logic.py`
  - реализовать простую очередь или state machine для состояний агента;
  - подготовить публикацию событий в Redis или HTTP callback в Java.
- `.env`
  - `OPENROUTER_API_KEY`
  - `OPENROUTER_MODEL`
- `requirements.txt`
  - `fastapi`
  - `uvicorn`
  - `openai`
  - `python-dotenv`
  - `pydantic`
  - `httpx`
  - `redis`

Технические решения:

- на первом этапе использовать HTTP между Java и Python для запроса генерации комнаты;
- для событий агентов выбрать один из двух вариантов:
  - быстрый MVP: Python вызывает Java callback endpoint;
  - более устойчивый путь: Python публикует события в Redis Pub/Sub.

Рекомендуемый порядок:

1. Health-check.
2. Мок-генерация комнаты без OpenRouter.
3. Интеграция OpenRouter.
4. Эмуляция событий агента.

Готовность фазы:

- Python принимает prompt и возвращает валидный JSON комнаты;
- сервис может генерировать минимум один сценарий без внешней модели.

## Phase 3. Java backend на Spring Boot

Цель: реализовать центральный orchestration слой.

Файлы и задачи:

- `CrabController.java`
  - `POST /api/rooms`
  - `GET /api/rooms/{id}`
  - `GET /api/rooms/{id}/history`
- `RoomService.java`
  - отправка запроса в Python сервис;
  - сохранение комнаты и агентов;
  - публикация событий во frontend.
- `WebSocketConfig.java`
  - настроить STOMP endpoint;
  - каналы вида `/topic/rooms/{roomId}`.
- `AgentDispatcher.java`
  - слушать Redis Pub/Sub или callback endpoint;
  - маппить события в frontend DTO;
  - отправлять их в WebSocket.
- `AgentEntity.java` и `RoomEntity.java`
  - JPA-модели;
  - связи `Room 1:N Agent`.
- `pom.xml`
  - Spring Web
  - Spring WebSocket
  - Spring Data JPA
  - Spring Validation
  - PostgreSQL Driver
  - Lombok
  - Spring Data Redis или Lettuce

Дополнительно стоит добавить:

- DTO для API и WebSocket;
- Flyway или Liquibase для миграций;
- конфигурацию `application.yml` с профилями `local` и `dev`.

Готовность фазы:

- Java умеет создать комнату через Python;
- PostgreSQL хранит комнату и агентов;
- WebSocket отдает событие создания комнаты и обновления статусов.

## Phase 4. Frontend на Next.js

Цель: отрисовать офис и обеспечить realtime UI.

Файлы и задачи:

- `pages/index.tsx`
  - форма ввода prompt;
  - выбор пресета офиса;
  - запуск создания комнаты;
  - загрузочные и error-состояния.
- `components/Office.tsx`
  - сетка комнаты;
  - рендер фона по preset;
  - рендер списка агентов.
- `components/PixelAgent.tsx`
  - пиксельный персонаж;
  - состояния `idle`, `walking`, `working`, `typing`;
  - анимации через Framer Motion.
- `hooks/useSocket.ts`
  - подключение к STOMP/WebSocket;
  - подписка на комнату;
  - обновление локального состояния.
- `public/assets/`
  - спрайты агентов;
  - тайлы фона;
  - декоративные элементы офиса.

UI-этапы:

1. Статичная страница с вводом prompt.
2. Отрисовка мок-офиса по JSON.
3. Подключение к Java API.
4. Подключение realtime событий.
5. Полировка пиксель-арт атмосферы.

Готовность фазы:

- пользователь может создать комнату из UI;
- агенты отображаются и меняют состояние в реальном времени.

## Phase 5. Сквозная интеграция

Цель: связать все три модуля в один рабочий сценарий.

Сквозные задачи:

- проверить создание комнаты из фронтенда до БД;
- проверить публикацию агентских событий от Python до UI;
- синхронизировать идентификаторы `roomId` и `agentExternalId`;
- добавить корреляционный `requestId` в межсервисные запросы;
- настроить CORS и origin policy для локальной разработки.

Готовность фазы:

- демонстрационный сценарий работает локально без ручных фиксов;
- офис создается и обновляется end-to-end.

## Phase 6. Улучшение механики агентов

Цель: перейти от простой отрисовки к ощущению живого офиса.

Задачи:

- ввести роли агентов: architect, developer, analyst, manager;
- описать допустимые состояния и переходы;
- добавить расписание или цикл задач агента;
- визуализировать перемещения между рабочими зонами;
- отображать краткие сообщения над агентами;
- добавить историю событий комнаты.

Если LangGraph будет использоваться, его лучше внедрять после рабочего MVP, а не в первой итерации. Для старта проще и надежнее сделать свою state machine и очередь событий.

## Phase 7. Надежность и эксплуатация

Цель: подготовить систему к стабильной локальной эксплуатации и дальнейшему росту.

Задачи:

- централизовать логирование во всех сервисах;
- добавить retry и timeout между Java и Python;
- предусмотреть fallback на мок-ответ при недоступности OpenRouter;
- добавить базовую авторизацию позже, но не блокировать MVP;
- ограничить частоту генерации комнат;
- добавить обработку повторных подключений к WebSocket.

## 5. Приоритеты реализации

Рекомендуемая очередность:

1. `docker-compose.yml` + переменные окружения.
2. FastAPI мок-генерация комнаты.
3. Spring Boot API + PostgreSQL persistence.
4. Next.js форма и отрисовка комнаты.
5. WebSocket pipeline.
6. Redis Pub/Sub для событий агентов.
7. OpenRouter integration.
8. Полировка пиксель-арт UI и поведения агентов.

Такой порядок снижает риск: сначала поднимается локально воспроизводимый MVP без внешней зависимости на LLM, потом добавляется интеллект и realtime-слой.

## 6. Definition of Done для MVP

MVP считается завершенным, если выполнены все пункты:

- инфраструктура поднимается локально;
- frontend создает комнату через backend;
- backend сохраняет данные в PostgreSQL;
- Python возвращает валидную структуру офиса;
- frontend отображает комнату и минимум 3 агентов;
- изменения статусов агентов приходят через WebSocket;
- есть README с командами запуска и переменными окружения;
- есть хотя бы базовые smoke-тесты для каждого сервиса.

## 7. Минимальный набор тестов

- Python: тест генерации структуры комнаты и валидации JSON.
- Java: тест сервиса создания комнаты и тест REST endpoint.
- Frontend: тест рендера офиса по JSON и тест хука сокета.
- Интеграция: smoke-сценарий создания комнаты end-to-end.

## 8. Основные риски

- нестабильный JSON от модели OpenRouter;
- избыточная сложность при раннем внедрении LangGraph;
- рассинхронизация схем событий между Python, Java и frontend;
- тяжелая анимация на фронтенде без ограничений по FPS и числу агентов;
- отсутствие fallback-сценариев при недоступности Redis, Postgres или OpenRouter.

## 9. Что делать следующим шагом

Следующая практическая итерация должна включать:

1. создать `docker-compose.yml` для Postgres и Redis;
2. сгенерировать каркас FastAPI, Spring Boot и Next.js приложений;
3. описать первые DTO и JSON-контракты;
4. реализовать вертикальный срез: `create room` от UI до БД без realtime;
5. затем добавить WebSocket и агентские события.
